## Rules

- **Overrides (R4):** a route may replace CSP or CORP only through `reply.securityOverride({ csp, corp })`. Find every use with `grep securityOverride(`. Right now only the unsubscribe page uses it. Swagger UI (`/docs`, `/docs/json`, `/docs/static/*`) is on by default only when NODE_ENV is exactly development or test. Any other environment returns 404 unless `API_DOCS_ENABLED=true` (any other value is off). When it is enabled there, every `/docs` request needs a signed-in browser session (the session cookie; bearers are not accepted) whose email is in `API_DOCS_ADMIN_EMAILS`: 401 without a valid session, 403 otherwise, and an empty list lets nobody in. The docs pages are served under the strict `DOCS_CSP` (`script-src 'self'`, no `unsafe-inline`) by the security-headers hook (path match, not `securityOverride`); every other route keeps `API_CSP` (`apps/api/test/hardening.test.ts`).
- **Errors (R5):** every 4xx and 5xx response is the `ApiErrorEnvelope`. It never contains a stack trace, file path or Prisma text (`apps/api/test/security-followups.test.ts`).
- **CORS (R7):** `WEB_ORIGINS` holds exact origins and is parsed at boot. A strict environment refuses to start on `*`, `null`, a path, a query, a trailing slash, credentials, a non-http(s) scheme, or `http://` in production.
- **Cookies (R13/R14):** the CSRF cookie is `__Host-`, `Secure`, `SameSite=Strict` and readable by JS, and its Max-Age equals the session's absolute timeout. The pre-session cookie is `HttpOnly` and `SameSite=Strict`, with a Max-Age of 1 hour. Logout, logout-all, revoking the current session and password reset clear the sid, CSRF and pre-session cookies.
- **Realtime (R19):** the baseline headers are added to every HTTP response, including the raw `HTTP/1.1 4xx` reply to a rejected WebSocket upgrade.
- **Web CSP (R20):** there is no `'unsafe-inline'`. Every inline `<script>` or `<style>` needs its hash in the template, and `pnpm --filter @meetops/web csp` checks this. When `CSP_UPGRADE_INSECURE=on` (the image default, used in production), the container refuses to start unless every `CSP_*_ORIGIN` is `https://` or `wss://`. The local compose stack sets it to `off`.
- **Vite (R24):** `vite dev` and `vite preview` send the template CSP with local origins. Dev also adds a per-process nonce, which `html.cspNonce` stamps on Vite's injected scripts and styles (`apps/web/csp.config.ts`).

## Dockerfile.web defaults

The image's default `CSP_API_ORIGIN`, `CSP_REALTIME_ORIGIN` and `CSP_STORAGE_ORIGIN` values are `http://localhost` and `ws://localhost` placeholders, and `CSP_UPGRADE_INSECURE` defaults to `on`. If you run the bare image without overriding them, it **refuses to start**. The startup error names the variable and the offending origin. To fix it, either:

- **Production / staging:** set every `CSP_*_ORIGIN` to the real `https://` / `wss://` origins.
- **Local plain-http stack:** set `CSP_UPGRADE_INSECURE=off`, as `infra/compose/compose.app.yml` already does.

## API content types (R16)

`apps/api/src/shared/json-only.ts` rejects POST/PUT/PATCH/DELETE requests that carry a body (content-length > 0 or transfer-encoding) unless the media type is `application/json`, with 415. Empty-body mutations are allowed. A route may opt in to other types with `config.allowedContentTypes`.

| Route                                                         | Type                                | Decision                                                          |
| ------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------------- |
| `POST /notifications/unsubscribe`                             | `application/x-www-form-urlencoded` | Allowlisted: RFC 8058 one-click unsubscribe from mail clients     |
| `POST /webhooks/:provider/:integrationId`, GitHub App webhook | JSON                                | JSON-only (providers send JSON; raw-buffer JSON parser)           |
| Uploads                                                       | n/a                                 | No multipart routes: uploads are presigned PUTs direct to storage |
| Beacons / CSP reports                                         | n/a                                 | None exist                                                        |

## CSRF rotation (R17)

Login, org switch and org create issue a new session and a new CSRF token bound to it; the pre-session cookie is cleared, so pre-login, pre-switch and pre-logout tokens get 403. The web client uses the `csrfToken` from login and drops its cached token after a switch, create or logout, so it reads the new one.
