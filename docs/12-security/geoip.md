# GeoIP session location (ADR-014)

Sessions and auth audit events carry a coarse, approximate location (`geoCity`, `geoRegion`, `geoCountry`,
`geoCountryCode`, `geoApproximate=true`). See [ADR-014](../15-decisions/ADR-014-geoip-session-location.md).

(`apps/api/src/shared/geoip/index.ts`).

## How it works

- **Data source:** the DB-IP City Lite `.mmdb` file, read into memory with the `maxmind` npm package. Lookups are local:
  no per-request external API, no API key, no paid provider and no automatic fallback. `GEOIP_PROVIDER=geolite2` reads
  a MaxMind GeoLite2-City file through the same `GeoIpProvider` interface.
- **Fields read:** city, first subdivision (region/state), country names (`en`) and the ISO country code. Latitude,
  longitude, accuracy radius and postal code are never read or stored.
- **Sanitising:** names are third-party input. Control, CR/LF, bidi/invisible characters and `<`, `>`, `"` are stripped,
  whitespace collapsed, length capped at 128, and IP-looking values dropped, to match the contracts `GeoName` rules.
  Renderers still escape output (`'` and `&` are allowed).
- **When:** at session creation and when a session's client IP changes, plus on every auth audit event. Private,
  reserved, documentation and unknown IPs give all-null fields, and `SessionSummary` then omits the geo fields.
- **Client IP:** Fastify `request.ip` after the `TRUST_PROXY` CIDR allowlist; `CF-Connecting-IP` only with
  `BEHIND_CLOUDFLARE=true` and a peer inside the pinned Cloudflare ranges (refresh via PR from
  `https://www.cloudflare.com/ips-v4` and `/ips-v6`). Raw `X-Forwarded-For` is never read.
- **Logs:** full IPs are never logged at info; the logger audit sink truncates to /24 (IPv4) or /48 (IPv6).
- **Missing database:** lookups are disabled (null provider) and sign-in keeps working.

## New-location sign-in alert

On a successful **password login**, the API compares the session's coarse location with the user's earlier sessions:

- **No alert** on the first sign-in with a known location (that sign-in is the baseline), for private or unknown IPs, or when the country (and region) has been seen before.
- **`new_country`** when the country code was never seen, and **`new_region`** when the country is known but the region was never seen there. A missing region on either side never triggers an alert on its own.
- **Limits** (per user, via the auth rate limiter): 1 alert per (country, region) per 24 h, and at most 3 alerts per user per 24 h. If the limiter or the history lookup fails, there is no alert and sign-in carries on.

The API writes the `auth.new_location_signin` outbox event **in the same transaction as the session**. Its payload is the strict contract `AuthNewLocationSigninEvent` (`sessionId`, `city`, `region`, `country`, `countryCode`, `reason`), so it **never carries an IP address**. The builder validates the payload against the schema and drops the alert if it doesn't match.

The notifications relay (ADR-013) claims this event kind. It notifies **only the signed-in user**, taken from the outbox aggregate rather than the payload, and only after re-checking membership. The notification is sent in-app and by email (email is on by default for this kind, and a user preference can turn it off). The feed item data is `{sessionId, reason, geoCity?, geoCountry?}`: unknown geo values are left out, never null. Notifications are deduplicated per user, location and UTC day.

The email:

- has a fixed subject with no location text;
- HTML-escapes the location in the body;
- shows the DB-IP attribution;
- links only to `WEB_BASE_URL/settings/sessions`. Revoking a session there needs a signed-in session plus CSRF. The email has no one-click token and no session id in the URL.

The worker sends it only when `WEB_BASE_URL` (https) is set and the shared `EMAIL_*` configuration loads. Otherwise the email channel is skipped; there is no fallback provider.

**Limitation (org only):** outbox events and notifications are organization-scoped (`outbox_events.org_id` is NOT NULL, ADR-013). The alert therefore fires only when the new session has an **active organization**, which is the user's last-used live membership. A user with no organization gets no new-location alert. The sign-in is still recorded with its geo in `sessions` and in the global audit event. Desktop and extension token sign-ins don't run this check.

## Test fixture

`apps/api/test/fixtures/geoip/test-city.mmdb` (about 2 KB) is **fictional** data generated by
`generate-fixture.py` in the same folder with `mmdb-writer` 0.2.7 (PyPI) and `netaddr` 1.3.0. It contains no DB-IP or
MaxMind data. Tests never download the real database.

## Getting the database

The monthly updater job (ADR-014 PR 6) will download and verify the file. Until then, download
`dbip-city-lite-YYYY-MM.mmdb.gz` manually from `https://download.db-ip.com/free/`, gunzip it, and point
`GEOIP_DB_PATH` at it.
