## 1. Summary

| #   | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| K1  | Today the sync is **create out, status in**. MeetOps creates one issue per approved task (API `pushIssue`, or the worker job behind `TASK_SYNC_ENABLED`), and GitHub `issues` / Jira `jira:issue_*` webhooks write the mapped status back onto `tasks.status`. No other field flows either way, and MeetOps never updates an issue after creating it (`updateStatus` exists in both adapters but nothing in `apps/` calls it).                        |
| K2  | The inbound write has **no ordering or echo guard**: `applyIssueStatus` overwrites `tasks.status` and `completed_at` on every mapped event (`apps/api/src/modules/integrations/prisma.repository.ts` L174–205). Replay protection only drops the same delivery id. A late or retried older event can roll status back.                                                                                                                                |
| K3  | **Jira inbound can't work with the OAuth app as built.** The receiver checks `X-Hub-Signature` against a per-connection secret, but webhooks an OAuth 2.0 app registers are "secured by bearer authentication ... signed with the app's client secret", expire after 30 days, need `manage:jira-webhook`, and are capped at 5 per app per user per tenant [S1, S2]. The runbook already flags that the secret is never registered with Jira (L72–75). |
| K4  | Jira's default rate tier is one **65,000-point hourly pool shared across all tenants** of an app, plus per-endpoint burst limits (GET/POST 100 RPS, PUT/DELETE 50) and per-issue write limits [S3]. Polling scales against that shared pool, so Jira should be webhook-first with light reconciliation.                                                                                                                                               |
| K5  | GitHub "does not automatically redeliver failed deliveries"; you can redeliver from the past 3 days, and must answer within 10 seconds [S6, S7]. Installation tokens get 5,000 requests/hour (scaling to 12,500; 15,000 on Enterprise Cloud) [S8]. A reconciliation sweep is needed either way.                                                                                                                                                       |
| K6  | Status categories make Jira mapping stable (`new` / `indeterminate` / `done`) [S4, S5], but "done" hides "Won't Do"-style outcomes. On GitHub, `state_reason` now includes `duplicate` [S10], which the repo maps to `done`; Projects v2 status is a separate single-select field behind the org "Projects" permission, and its webhook is org-level and in public preview [S9].                                                                      |
| K7  | The "since last meeting" data is mostly there (`tasks.meeting_id`, `integration_issues`, calendar links), but there is **no series key**: Google instances are fetched with `singleEvents=true` and `recurringEventId` is dropped, and the Outlook `$select` omits `seriesMasterId` (`packages/integrations/src/calendar.ts` L276, L299–314; `calendar-outlook.ts` L77). Attendee emails aren't stored either (only `attendee_count`).                |
| K8  | Of the competitors checked, only Microsoft's Loop task lists document a true two-way sync (with Planner). Most others push action items one way; Otter adds a read path through an AI chat connector, and Asana and Zoom keep tasks native. Asana and Zoom document the closest thing to "since last meeting" (§7).                                                                                                                                   |

## 3. Conflict model

### 3.1 Options

| Option                               | How it works                                                                                                                                                          | For                                                                                  | Against                                                                                                                                                                  |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A. Last-writer-wins by timestamp     | Compare MeetOps `updated_at` with the provider's (`issue.updated_at` on GitHub, `fields.updated` on Jira).                                                            | Simple, symmetric.                                                                   | Clocks differ; a field-level change loses to an unrelated later edit of another field; silent data loss.                                                                 |
| B. Last-writer-wins by version (CAS) | Store the provider version we last saw; before writing, re-read and write only if unchanged, else re-merge. Inbound events older than the stored version are dropped. | No clock trust; prevents rollbacks; matches `lastKnownStatus` "for conflict checks". | Extra GET per write (rate budget); GitHub has no ETag-style conditional PATCH for issues that we found, so it's read-then-write with a race window (**interpretation**). |
| C. Source of truth per field         | Each field has one owner once linked. Non-owner edits are either blocked in the UI or shown as "changed in Jira".                                                     | No merge logic; easy to explain; no loops for owned fields.                          | Users expect to edit everywhere; needs clear UI.                                                                                                                         |
| D. Ask the user                      | Detect divergence (both sides changed since last sync) and show a "keep MeetOps / keep Jira" prompt.                                                                  | No silent loss.                                                                      | Prompts pile up; nobody answers them in a meeting tool.                                                                                                                  |

### 3.2 Field by field (proposal: C, with B for the two-way fields and D only for status)

| Field       | Owner after link       | Direction                                                                               | Notes                                                                                                                                                                                         |
| ----------- | ---------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Title       | Provider               | Out at create; in afterwards (display)                                                  | People rename tickets in the tracker. Keep the MeetOps original as "from the meeting".                                                                                                        |
| Description | Provider               | Out at create only                                                                      | Never overwrite a provider description; it may have been rewritten. The meeting quote and timestamp (spec 01) stay in MeetOps.                                                                |
| Assignee    | Provider               | In (display)                                                                            | No mapping exists between `employees` and Jira `accountId` / GitHub login. Show the provider name until a mapping table exists; don't write assignees out.                                    |
| Status      | Both (two-way)         | In via webhook; out only on an explicit user action, through the existing approval gate | CAS on `last_known_status` + provider version. If both changed since last sync, the provider wins and the user sees "changed in Jira" (D, lightweight).                                       |
| Due date    | Provider (Jira only)   | Out at create if set; in afterwards                                                     | Jira has `duedate`; GitHub Issues has no due date (Projects date fields or milestones only), so GitHub is out of scope.                                                                       |
| Priority    | Provider (Jira only)   | In (display), mapped by name                                                            | Jira priorities are per-site schemes (**interpretation**); keep the raw name and map known names to `TaskPriority`, else leave MeetOps' value. GitHub has none.                               |
| Labels      | Provider               | Out at create: one `meetops` label (optional); in: display only                         | Don't mirror labels. Note GitHub's in-progress convention is itself a label (`status: in-progress`, `github.ts` L45).                                                                         |
| Comments    | Each side owns its own | In: metadata (count, last author, last time) for the digest; out: none in phase 1       | Comments are append-only, so there's no conflict. Posting meeting notes as comments is a later, approval-gated write. Store metadata, not comment text, to keep personal data out of MeetOps. |

### 3.3 Loop and echo prevention (proposal)

1. **Origin flag:** a change applied from a webhook is marked `origin = provider` and never queued outbound.
2. **Actor check:** drop inbound events whose actor is our own app. GitHub: `sender` is the App's bot user; Jira: the
   event's `user.accountId` equals the account that authorised the connection (**UNVERIFIED** for both until a real
   install shows the payloads).
3. **Write ledger:** after each outbound write, store the provider version and a hash of what we wrote. An inbound
   event that matches it is acknowledged without a change.
4. **Monotonic apply:** keep `provider_updated_at` per link and drop older events. This also fixes K2.
5. **Idempotent keys:** keep ADR-007's delivery-id replay store, and use the existing `meetops-ref` marker to find
   our own issue before retrying a create that failed with a 5xx (ADR-007 "Consequences").

**Recommendation (proposal):** ship per-field ownership with provider-wins for everything except status; make status
two-way with CAS and the existing approval gate; add the monotonic guard to the current inbound path first, since it
fixes a live bug.

## 4. Webhooks versus polling

| Topic               | Jira Cloud                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | GitHub Issues                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Events we'd need    | `jira:issue_created`, `jira:issue_updated` (with a `changelog` of field changes), `jira:issue_deleted`, `comment_created` / `_updated` / `_deleted`; JQL filtering is supported for issue and comment events [S1].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | `issues` actions include `opened`, `closed`, `reopened`, `edited`, `assigned`, `unassigned`, `labeled`, `unlabeled`, `deleted`, `transferred`, `milestoned`, `status_changed` (issue statuses, "in preview") and more; `issue_comment` (`created`, `edited`, `deleted`, ...); `projects_v2_item` for org projects (public preview) [S9].                                                                                                        |
| How it's registered | Admin-created webhook (optional secret), or dynamic registration by an OAuth 2.0 app: `POST /rest/api/3/webhook`, scopes `read:jira-work` + `manage:jira-webhook`; expires after 30 days, extended with `PUT /rest/api/3/webhook`; 5 webhooks per app per user per tenant; "for non-public OAuth apps, webhooks are delivered only if there is a match between the app owner and the user who registered" [S1, S2].                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | One App webhook URL and secret for all installations (runbook L53), routed by `installation.id` (`service.ts` L305); events chosen in the App settings.                                                                                                                                                                                                                                                                                         |
| Verification        | Admin webhooks with a secret: HMAC in `X-Hub-Signature` as `method=signature`. OAuth 2.0 app webhooks: a bearer JWT in `Authorization`, signed with the app's client secret [S1].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | HMAC-SHA256 in `X-Hub-Signature-256` with the App secret [S11]. `X-GitHub-Delivery` is a unique id for replay checks [S7].                                                                                                                                                                                                                                                                                                                      |
| Delivery and retry  | Up to five retries, 5–15 minutes apart, on 408, 409, 425, 429, 5xx or connection failure; so some webhooks "might be delivered more than once". `X-Atlassian-Webhook-Identifier` is stable across retries. After 30 minutes of failure, one attempt per webhook until success. Primary webhooks within 30 s. Concurrency 20 (primary) / 10 (secondary) per tenant + host. "Get failed webhooks" is for Connect apps only [S1, S2].                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Respond with 2XX within 10 seconds or it counts as failed; GitHub "does not automatically redeliver failed deliveries"; manual or scripted redelivery for the past 3 days [S6, S7]. No ordering guarantee is documented (we found none).                                                                                                                                                                                                        |
| Rate limits         | Three systems: points-based hourly quota (Tier 1 global pool of 65,000 points/hour shared across all tenants; Tier 2 per-tenant pools only after review), per-endpoint burst (GET 100, POST 100, PUT 50, DELETE 50 RPS by default) and per-issue write limits. Base cost 1 point, plus object costs on reads; writes cost 1 point. 429 with `Retry-After` and `RateLimit-Reason`. Atlassian's changelog says phased enforcement of the points-based quota for Jira and Confluence REST APIs began on **2 March 2026**: it started "with a small percentage of apps" and expanded "over several weeks"; GraphQL follows later and API-token traffic is not affected. A `Beta-` prefix on the quota headers (e.g. `Beta-RateLimit-Policy`) means enforcement hasn't started for that app yet [S18]. The rate-limiting page still says enforcement "will begin on March 2, 2026" [S3]. | REST: installation 5,000/hour, +50 per repo over 20 and +50 per user over 20, max 12,500; 15,000 on Enterprise Cloud; OAuth apps and user tokens 5,000 (15,000 Enterprise Cloud) [S8]. GraphQL: 5,000 points/hour per installation (scales to 12,500; 10,000 Enterprise Cloud) [S12]. Secondary: 100 concurrent requests, 900 points/minute REST and 2,000 GraphQL, CPU-time caps, about 80 content-creating requests/minute and 500/hour [S8]. |
| Polling cost        | JQL search on `updated >= -Nm` per tenant uses the shared pool. **Estimate:** 100 tenants × 12 polls/hour × (1 + ~20 issues) ≈ 25,000 points/hour, a third of the Tier 1 pool, before any user traffic.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | One `GET /repos/{o}/{r}/issues?since=...` per repo per poll against each installation's own budget. Cheap per tenant (**estimate**).                                                                                                                                                                                                                                                                                                            |

**Recommendation (proposal):**

- **Jira:** webhook-first via dynamic registration at connect (add `manage:jira-webhook`; verify the JWT with the
  client secret; a daily job extends webhooks before day 30). Keep the admin-webhook + HMAC path as a fallback for sites
  that won't allow it, and show the secret once in settings. Add a low-frequency reconciliation (hourly JQL over linked
  keys only) to catch missed events. **UNVERIFIED:** JWT claims, the actor field, and how the 5-per-user cap and the
  "non-public app" rule play out for our app's distribution.
- **GitHub:** keep the App webhook; queue processing so the handler always answers within 10 s; a sweep every few
  minutes lists failed App deliveries and redelivers them (within the 3-day window); a nightly re-read of linked issues
  updated since the last sweep.

## 8. "Since last meeting" digest

### 8.1 Content (proposal)

1. **Status changes** on tasks from earlier instances of the series since the last instance, with who changed them
   (provider actor name) and where.
2. **Overdue:** `tasks.due_at < now()` and status not `done`/`cancelled`.
3. **Closed elsewhere:** status moved to `done`/`cancelled` by a provider event, not in MeetOps.
4. **New comments:** count and last comment time per linked issue (metadata only).
5. **Still open, carried N times** (spec 02's carry count) and **no owner** items.
6. **Stale links:** links with `synced_at` older than a threshold or marked "unmapped"/"broken".

### 8.2 Finding the previous meeting (options)

| Option                       | Data needed                                                                                                                     | For                            | Against                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------- |
| Series key from the calendar | Google `recurringEventId` (present on instances with `singleEvents=true`) or `iCalUID`; Graph `seriesMasterId` [spec 02 R1, R2] | Exact; cheap                   | Needs `calendar_events.series_key`; Graph `$select` must add it (**UNVERIFIED** on `calendarView/delta`). |
| Heuristic                    | Same `organizer_email`, normalised title, similar weekday/time, within ~35 days                                                 | Works for non-recurring events | False matches ("1:1", "Sync"); attendee overlap would need attendee data we don't store.                  |
| Manual link                  | Host picks "previous meeting"                                                                                                   | Always right                   | Effort                                                                                                    |

**Recommendation (proposal):** series key first, manual link as the override, heuristic only as a suggestion the host
confirms. If attendee overlap is wanted, store keyed hashes of attendee emails rather than the emails, and ask counsel
only if that design changes (no counsel question proposed now).

### 8.3 Data sources

`tasks` (`meeting_id`, `status`, `due_at`, `assignee_id`), `integration_issues` (plus the new columns in §9),
`calendar_event_links` → `calendar_events` (series key), a new `integration_issue_events` history table for "changed
since", and spec 02's `task_carryovers`.

### 8.4 When it's shown (proposal)

1. **In-meeting / meeting page panel first:** read-only, computed on open (web meeting page; extension and desktop side
   panel; mobile meeting screen).
2. **Pre-meeting notification second:** T-30 minutes by default, org members only (ADR-013 fan-out), in-app feed item
   plus push. Push text stays generic (`GENERIC_PUSH_TITLE` / `GENERIC_PUSH_BODY` in
   `packages/contracts/src/api/notifications.ts` L46–47), so no task text leaves through push providers.
3. **Email later**, opt-in.
