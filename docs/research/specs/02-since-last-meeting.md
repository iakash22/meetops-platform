# Spec 2: "Since last meeting" view of live task status

- Proposal #2 in PR #468 (P0). Gap G5: summaries don't turn into tracked work, and nobody checks last week's items.
- Evidence: competitors push tasks one way (Fireflies → Linear, #468 S21; tl;dv → Jira and others, S4b) or sync through
  Zapier (Fellow ↔ GitHub, S25). We found no live status view across instances of a recurring meeting (weak evidence; see
  #468's blue-ocean caveat).

## 1. User stories

1. As the **host of a weekly sync**, when I open this week's meeting I see every task created from the last instance and
   its live GitHub/Jira status.
2. As a **participant**, I get a short pre-meeting digest: overdue, done, still open, and items with no owner.
3. As a **lead**, I see "carried over 3 weeks running" items so we decide to drop or escalate them.
4. As an **org admin**, I can turn the digest off, or limit it to org members (it never goes to external attendees; see
   spec 4).

## 2. UX flow

1. A meeting linked to a calendar event (`calendar_event_links`) that belongs to a **series** gets a "Since last meeting"
   panel on its page (`apps/web/src/features/meetings/meetings-pages.tsx`, next to `insights-panels.tsx`).
2. The panel lists tasks whose `meetingId` is any earlier instance in the series (default: the previous one; toggle "last
   4"). Columns: title, owner, status chip (from `tasks.status` and the linked issue), due date, "carried N times", link to
   the GitHub/Jira issue.
3. 30 minutes before the next instance (configurable), a digest goes to org-member attendees through the notifications
   pipeline (ADR-013), in-app first, email optional.
4. In the meeting, the host can tick "discussed" on each carried item; that's stored for the next carry count.

## 3. Data model and API sketch

Today:

- `CalendarEvent` and `CalendarEventLink` (`packages/database/prisma/schema.prisma`) hold `providerEventId`, times,
  organiser and `meetingId` links (manual or auto). **There is no series field**, and the worker sync
  (`apps/worker/src/calendar/sync.ts`) doesn't read recurrence fields.
- Providers expose the series: Google Calendar events carry `recurringEventId` and `iCalUID` [R1]; Microsoft Graph events
  carry `seriesMasterId` [R2].
- `Task.meetingId` and `Task.extractedTaskId` link tasks to meetings. `IntegrationIssue` links tasks to GitHub/Jira
  (`provider`, `externalId`, `externalUrl`, `syncedAt`). The contracts type has `lastKnownStatus`
  (`packages/contracts/src/domain/task.ts`), but the DB model has **no** such column.
- Status comes back through `packages/integrations/src/status-sync.ts` (GitHub `issues` webhook → `StatusChange`) and
  `packages/integrations/src/jira-webhook.ts`; sync is behind `TASK_SYNC_ENABLED`
  (`apps/api/src/modules/integrations/task-sync.ts`).

Proposed:

- Migration: `calendar_events.series_key text null` (Google `recurringEventId` or `iCalUID`; Graph `seriesMasterId`),
  index `(org_id, series_key, starts_at)`. Worker sync fills it.
- Migration: `integration_issues.last_known_status` (enum matching contracts `IssueStatus`) and `status_changed_at`, set
  by the status-sync handler. This closes a contracts/DB gap.
- Migration: `task_carryovers (org_id, task_id, meeting_id, discussed boolean, created_at)`, append-only, RLS like the
  other org tables.
- Read API (new, read-only, all roles with meeting read access):

```ts
// GET /orgs/:organizationId/meetings/:meetingId/since-last
type SinceLastResponse = {
  seriesKey: string | null; // null => not part of a series; client hides the panel
  previousMeetingIds: string[]; // newest first, max 4
  items: Array<{
    taskId: string;
    title: string;
    status: TaskStatus; // packages/contracts/src/domain/task.ts
    issue?: {
      provider: 'github' | 'jira';
      externalId: string;
      externalUrl?: string;
      lastKnownStatus?: IssueStatus;
    };
    assigneeId?: string;
    dueAt?: string;
    carriedCount: number;
    fromMeetingId: string;
  }>;
};
```

- Digest: an outbox event `meeting.pre_digest` on schedule (`apps/worker/src/calendar/scheduler.ts`), fanned out by the
  ADR-013 worker to **org members only**.

## 4. AI approach

- No AI is needed for the core view (it's a join).
- Optional: a one-paragraph "what changed" summary from task status deltas, generated by the existing LLM route (ADR-009)
  and labelled as AI-generated (see legal brief §3 on Art. 50).
- Optional later: match a new action item to an open carried task ("this is the same as last week's 'migrate CI'") by
  embedding similarity (`meeting_embeddings`, P7), shown as a suggestion only.

## 5. Risks

- **Depends on owner-blocked work:** live GitHub/Jira sync (P5: Jira credentials, GitHub App install, HANDOFF §5) and the
  Google Calendar OAuth client. Without them the view shows MeetOps task status only.
- Series detection fails for ad-hoc meetings that aren't recurring events. Fallback: let the host link "previous
  meeting" manually.
- Digest leakage to external attendees. Mitigation: org-member-only recipients (ADR-013 fan-out re-checks membership),
  plus a test in spec 4.
- Webhook gaps make the status stale. Show `syncedAt` and a "refresh" action; ADR-007 replay handles retries.

## 6. Success metrics (targets are estimates)

- ≥50% of recurring meetings with tasks have the panel opened at least once (pilot orgs).
- Share of carried tasks closed within 2 instances rises against a pilot baseline.
- Digest opt-out rate under 20%.
- Status freshness: 95% of linked issues have `syncedAt` within 15 minutes of the provider event.
