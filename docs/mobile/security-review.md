### R5 note: the recorder file while recording (Tester r3)

expo-audio 0.3 writes one plaintext file in the app cache while recording; it can't encrypt in-stream. Mitigations: the
file is marked in-progress before `record()`, iOS sets backup exclusion + file protection on it right after `prepare`
(fail closed), Android's app cache is private and FBE-encrypted, Stop seals it into encrypted chunks and deletes it
before the marker clears, and launch deletes the marked file and sweeps recorder files from the cache.

Segment rotation (shorter plaintext windows) was **removed**: it turned one meeting into many recordings. Keeping one
recording per meeting with segments as chunks of the same upload is **not possible without a server/contract change**:
expo-audio's m4a segments aren't byte-concatenable, and the concatenable outputs (Android AAC-ADTS / MPEG-TS) aren't in
`ALLOWED_MEDIA_MIME_TYPES` (iOS AVAudioRecorder has none). Options: allow `audio/aac` and record ADTS, or server-side
remux of multi-part uploads. Tracked as a follow-up; not shipped here.

## Other hardening in M6

- Android `blockedPermissions` strips `READ/WRITE_EXTERNAL_STORAGE` and `SYSTEM_ALERT_WINDOW` (Expo defaults MeetOps doesn't use).
- `expo-dev-client` added so the `development` EAS profile (`developmentClient: true`) builds.
- Recording ids are allowlisted (`[A-Za-z0-9_-]`) before they touch a file path.
- No auto-start, background trigger or hidden capture path: capture begins only in the notice confirmation handler.
