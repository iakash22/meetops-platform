# Rate-limit coverage review (P9 item #9)

Every HTTP route in `apps/api`, plus the realtime and worker surfaces, and the limiter that covers it. Reviewed
9 Nov 2026 (IST) against `integration/phase-1` `c60fadcf` (route list dumped from a test-mode `createServer()`
via Fastify `onRoute`, then checked by hand). This supersedes the 3 Nov table (#416 coverage pass).

## How limits work

- One port, `RateLimiter` (Redis fixed windows in production, in-memory in tests).
- New buckets go through `consumeGuarded` (`apps/api/src/shared/guarded-limit.ts`): over the limit -> `429
RATE_LIMITED` + `Retry-After`; limiter error or no answer within 1.5 s -> `503 PROVIDER_UNAVAILABLE` +
  `Retry-After: 5` (fail closed, never an unmetered pass). Media uses the same behaviour in its own helper.
- Central config for the routes this review added: `ROUTE_RATE_LIMITS` in `apps/api/src/shared/rate-limits.ts`
  (`routeLimiter(...).charge(scope, who)`). Module-owned configs stay next to their code: `AUTH_LIMITS`,
  `INVITE_LIMITS`, `EXTENSION_LIMITS`, `DESKTOP_LIMITS`, `RESOLVE_LIMITS` / `CREATE_LIMITS`,
  `SEARCH_RATE_LIMIT` / `SEARCH_ORG_RATE_LIMIT` / `SEMANTIC_SEARCH_ORG_RATE_LIMIT`, `MEDIA_RATE_LIMITS`,
  `WEBHOOK_RATE_LIMITS`, `NEW_LOCATION_LIMITS`.
- Keys. Authenticated: `rl:<scope>:org:<org>:user:<user>` (after the tenancy check, so a caller from another org
  gets the usual 404 and charges nothing) plus an org ceiling `rl:<scope>:org:<org>` charged only after the user
  bucket allowed the request (one user cannot spend more of the org budget than their own cap; no org can reach
  another org's keys). Public: `rl:<scope>:ip:<ip>` where `ip` is `requestMeta().ip`, i.e. ADR-014 `clientIp`
  (TRUST_PROXY allowlist, or `CF-Connecting-IP` only from a pinned Cloudflare edge). Raw `X-Forwarded-For` is
  never a key.

## Gaps fixed in this PR

1. Presigned GET minting (`download-url`), analytics aggregates, calendar event reads (provider calls), OAuth
   connect/callback, issue push / task sync (provider writes), push-device registration, org creation and the
   public unsubscribe link had no limiter.
2. `POST /invitations/accept` keyed its per-IP bucket on `request.ip`. Behind Cloudflare that is the edge address,
   so every user shared one bucket (and one attacker could lock others out); it now uses the ADR-014 client IP and
   adds a per-user bucket so rotating IPs does not help token guessing.
3. Webhook and invitation limiters called `consume` directly: a Redis error became an unhandled 500 and a hung
   Redis held the request until the client timeout. Both now fail closed with 503 + Retry-After via
   `consumeGuarded`.

## Not covered (deliberately)

- **Org-scoped CRUD and plain reads** are not limited per route. They are tenant-scoped DB reads/writes (list
  routes are capped at `MAX_PAGE_LIMIT`) with no provider fan-out; a per-route bucket for each would add a Redis round trip to
  every request for little value. Recommendation: one global per-IP / per-session limit at the edge (CDN/WAF or
  nginx `limit_req`) before launch; tracked as a follow-up, not code here.
- **`/ready`** is not put behind the Redis limiter on purpose: it must keep answering when Redis is down (that is
  what it reports), and probes are already coalesced. Keep it (and `/metrics`) reachable only from the load balancer
  / monitoring network.
- **Media keys** stay per user (`media:*:user:<id>`) rather than per org + user. That is stricter (one budget across
  all of a user's orgs) and changing it would reset tuned production buckets; no cross-tenant spend is possible
  because the key is the caller's own user id. Per-IP legs (`*:ip:<ip>`, including `chunkPerSessionIp`) use the
  platform `clientIpKey` helper: a missing or invalid client IP fails closed with 503 + Retry-After instead of
  pooling into a shared `unknown` bucket.
- **Realtime** limits are in-process per replica. Its per-IP key (connection rate and concurrent-socket cap) now
  uses the same ADR-014 client IP as the API: `TRUST_PROXY` allowlist and `BEHIND_CLOUDFLARE`, parsed and resolved
  by the shared `packages/config/src/client-ip.ts` (`@fastify/proxy-addr`, the library behind Fastify's
  `request.ip`). `REALTIME_TRUST_PROXY_HOPS` was removed (a non-zero value fails startup). `meeting:join` keys on
  the socket id, so it is unchanged.
- **Auth routes** (including Google OIDC) are out of scope for #9 and are reviewed separately.

## Tests

`apps/api/test/route-rate-limits.test.ts`: for every new bucket, 429 + Retry-After over the limit, 503 +
Retry-After 5 when the limiter store throws, another user of the same org and the owner of another org are not
throttled; per-org ceiling isolation (org A exhausting its org bucket leaves org B at 200); a cross-org request is
404 and charges no bucket; public routes key on the ADR-014 client IP (TRUST_PROXY allowlisted peer uses the
forwarded address, an untrusted peer's `X-Forwarded-For` is ignored); invitation accept per-user bucket holds
across rotating IPs; webhooks answer 503 when the store is down (was 500); `routeLimiter` unit tests (key shape,
org charged after user, store error and hung store both fail closed). Existing suites still cover search
(`search.test.ts`, `search-org-cap-timeout.test.ts`), media (`media-rate-limit*.test.ts`) and webhooks
(`integrations-webhook-rate-limit.test.ts`).
